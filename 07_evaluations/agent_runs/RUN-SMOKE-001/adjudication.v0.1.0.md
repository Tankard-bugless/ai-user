# 七项专家能力冒烟测试复核

## 1. 总结

本轮采用盲测生成与独立评估分离的方式，选择六位专家和研究总控各 1 条高风险用例。

结果必须分两层解释：

| 观察层 | 结果 | 含义 |
|---|---:|---|
| 精确机器合同通过 | 1/7 | 只有 CTRL-01 的产物、路由、决策和行为标签全部与合同精确一致 |
| 核心决策方向正确 | 7/7 | 七条回答均作出了合同所要求的核心判断 |
| 全部必需行为被观察到 | 6/7 | CAP-03 缺少可定位的实际事实来源 ID/版本，其余六条完整 |
| 禁止行为出现 | 0/7 | 没有确认偏误、错误外推、虚假金融事实、越权审批、删反例、假漏斗或跳 Gate |
| 人工语义复核 | 未执行 | 当前复核由根 Agent 完成，不冒充人工审批或人工模型评测 |

因此，`1/7` 不能简单解释为“六位专家能力失败”。它反映了两类问题混在一起：

1. **真实输出契约缺口**：CAP-05、CAP-06 没有显式写出下一路由；CAP-03 没有给出可定位的事实来源版本。
2. **测试合同歧义**：部分情境缺少生成正式产物所需输入，但期待值仍要求立即生成产物并进入下游，导致谨慎地请求补充信息反而被判错。

## 2. 测试设计

- 待测方：3 个相互独立的盲测批次 Agent；每个批次只读取被分配的能力卡和情境，不读取期待答案。
- 原始回答：先合并并冻结到 `raw-outputs.jsonl`。
- 评估方：2 个未参与生成的独立评估 Agent；读取冻结回答和合同，保守标注实际行为。
- 评分：结构化评分器对产物、路由、决策、必需行为和禁止行为进行精确比较。
- 限制：同一待测批次承担了 2—3 项能力，因此这仍是低成本冒烟测试，不等于七个长期隔离 Agent 的生产验证。

## 4. 对专家能力的实际结论

### 已验证的安全边界

- CAP-01 不接受预设结论。
- CAP-02 不用定性便利样本估计总体比例。
- CAP-03 不凭常识或业务压力编造金融事实。
- CAP-04 不把质量预审冒充正式审批。
- CAP-05 不删除反例。
- CAP-06 不把不同构念伪装成同一漏斗。
- CTRL-01 不允许绕过 Gate 2。

### 需要改进的运行契约

1. CAP-05 和 CAP-06 的输出模板应增加必填 `next_route`，避免内容正确但无法被总控稳定接续。
2. CAP-03 的金融事实判断应区分：
   - 已提供适用事实库：必须引用具体 fact_id 和版本；
   - 未提供或来源冲突：必须输出 `FACT_REVIEW_REQUIRED` 并路由人工事实审核。
3. 测试套件需要统一 `route` 的含义：它究竟表示“当前立刻需要的输入方”，还是“正式产物完成后的下游能力”。两者不能混用。
4. 要求生成正式 Artifact 的用例必须同时提供 Schema 最低必要输入；否则期待值应允许 `WAITING_INPUT` 或 `NONE`。

## 5. 是否修改能力卡

本轮不直接改写能力卡或测试期待值。原因是：

- 真实 Agent 原始回答和独立评估需要保持冻结；
- 测试失败首先用于诊断，不应为了提高通过率立即改答案；
- 修改前应由研究负责人确认 `route` 的统一语义和缺少输入时的状态口径。

确认后，应产生新版本测试合同并运行 `RUN-SMOKE-002`，不得覆盖本次结果。
