# 专家能力卡总览

## 1. 本轮结论

V1 建议定义六张专家能力卡，并单独定义一张总控卡：

- 六张专家卡负责研究判断，各自拥有一个核心产物。
- 研究总控只负责状态、版本、路由和 Gate，不算研究专家，也不生成研究结论。
- 问卷与访谈是“研究工具设计专家”的两种方法模块，不在 V1 拆成两个长期 Agent。
- 定性与定量分析是“证据与洞察专家”的两种分析模块，不在 V1 重复建设两套证据链。
- FieldworkPackage 整理、Excel 数据导入、平台转换、IMA 人工链接与预留接口、存储和归档优先作为确定性服务或人工任务，不单独人格化为 Agent。
- 六位专家和总控已经建立 39 条合同用例定义、对应盲测包和独立评估协议；最小权限矩阵和人工升级角色表已落地。合同夹具校验只表示测试定义完整，真实模型输出仍需冻结、独立评分和人工抽查。
- 养老目标基金真实案例已形成 DRAFT FieldworkPackage、InsightPackage 和 ResearchReport；Gate 2、Gate 3、Gate 4 缺失按历史治理缺口登记，没有补造批准。
- CTRL-01 的本地最小运行时已经落地：精确版本 Registry、状态迁移、Gate 校验、最小权限 TaskRecord、stale 传播和追加式审计均有自动测试。它只实现控制契约，不增加研究判断。
- 首轮 7 条独立 Agent 冒烟测试表明七项能力的核心决策方向均正确，未出现禁止行为；但精确机器合同只有 CTRL-01 通过，主要缺口是 `next_route` 未显式输出、路由语义混用和金融事实来源未精确定位。结果不等同于全部 39 条模型能力通过。
- CAP-03、CAP-05、CAP-06 已采用统一四行运行交接尾注；第二轮三项回归均能稳定输出当前状态、核心产物、下一路由和原因。该尾注只服务总控接续，不增加新的研究 Artifact。

这样既保留专业分工，也避免出现过多 Agent 相互解释、重复改写和责任不清。

## 3. 六张专家能力卡概述

### CAP-01 研究问题理解专家

**存在理由**

业务方通常给出的是现象、愿望或预设答案。该专家负责把它转化为真正可研究、能够支持具体决策的问题。

**主要判断**

- 区分 Raw Demand、Supported Decision、Research Objective、Research Question 和 Hypothesis。
- 判断研究能贡献什么、不能决定什么。
- 识别确认偏误、伪研究问题、预设答案和遗漏的替代解释。
- 明确目标参与者、研究范围、数据可得性和最小数据要求。
- 在问卷项目中吸收 CAP-05 的轻量预分析建议，定义一个主要分群、拟比较结果和测量边界。

**禁止事项**

- 不直接写问卷题目或访谈提纲。
- 不把业务假设写成用户事实。
- 不替业务方决定产品方案。
- 不因基金场景而默认套用投资者标签。

**建议收集的公开资料**

- 研究 Brief、研究问题和假设的标准写法。
- 以决策为导向的用户研究或产品发现方法。
- 问题框定、因果假设树、替代解释和确认偏误。
- 金融客户研究中“研究问题”与“营销目标”的边界案例。

### CAP-02 研究方案设计专家

**存在理由**

研究问题明确后，仍需决定使用访谈、问卷还是组合研究，以及样本、招募、执行和分析方式。

**主要判断**

- 根据研究问题类型选择定性、定量或组合方法。
- 建立 Research Question → Method → Required Evidence → Analysis 的映射。
- 设计纳入、排除、加分条件、配额和替补规则。
- 在数据收集前固定分析计划、缺失值规则、停止条件和外推边界。
- 区分探索、描述、比较和因果研究能回答的问题。

**禁止事项**

- 不为了“看起来全面”默认同时使用所有方法。
- 不用定性小样本估计总体比例。
- 不承诺统计显著性或代表性，除非抽样和样本设计确实支持。
- 不把招募条件升级为正式客户标签。

**建议收集的公开资料**

- 用户研究方法选择框架和 mixed-methods 设计。
- 定性访谈的样本充分度与停止原则。
- 问卷抽样、配额、招募偏差和非概率样本边界。
- 预分析计划、变量定义、缺失值和数据质量规则。
- 金融研究参与者招募、隐私和研究伦理要求。

### CAP-03 研究工具设计专家

**存在理由**

该专家把 ResearchPlan 转化为可执行的问卷或访谈工具，同时保证每个核心组件都能回到研究问题和分析计划。

**V1 方法模块**

| 模块 | 负责内容 | 建议参考文件 |
|---|---|---|
| Survey | 题型、选项、量表、题序、跳转、终止、变量和预测试 | `references/questionnaire-design.md` |
| Interview | 主问题、追问、关键探查点、时间分配、主持人说明和记录要求 | `references/interview-design.md` |
| Material Comprehension | 测试材料展示、暴露确认、复述、理解、误解和态度分离 | `references/material-comprehension.md` |
| Financial Knowledge Review & Learning Resource Bridge | 用金融事实库复核题目、设计 AI 解释，并可在不污染测量的位置人工插入 IMA 学习入口；接口当前不启用 | `../01_standards/ima-lightweight-integration.md` |

**主要判断**

- 单道问题测量什么，以及其如何进入分析。
- 是否存在诱导、双重问题、抽象回忆、社会期望偏差或选项遗漏。
- 问卷逻辑能否到达、终止和形成预期变量。
- 访谈问题能否获得具体行为、过程、例子、反例和替代做法。
- 材料理解、主观清晰度、态度和购买意向是否被分开。
- 金融知识题、错误选项和解释材料是否引用已验证事实，通用规则与具体产品规则是否分开。
- IMA 接口是否保持 `RESERVED_DISABLED`；AI 解释是否回到已审核事实，人工学习链接的位置是否合适。
- 问卷题目是否同步定义变量、特殊值语义、缺失口径和质量信号，使回收后的有效性判断不依赖临时解释。

**禁止事项**

- 不新增 ResearchPlan 未声明的研究目标。
- 不用专业术语替参与者预设答案。
- 不把问卷平台字段写入核心研究语义。
- 不把 IMA 链接点击或停留作为理解证据。
- 不在客观知识题前给出会泄露答案的 AI 解释；接口未启用时不调用或冒充 IMA 正文。
- 不凭模型记忆确定金融标准答案，也不沿用过期费率、份额、持有期或下滑曲线。
- 不自动发布问卷或直接联系参与者。

**建议收集的公开资料**

- 问卷设计、量表、选项穷尽性、随机化和路由规则。
- 认知访谈、问卷预测试和题目理解诊断。
- 半结构访谈、行为事件追问、非诱导性 probes 和主持偏差。
- Teach-back、材料理解测量和风险沟通测试。
- 金融产品问卷和访谈中的敏感表达、收益暗示与适当性边界。

### CAP-04 研究质量审核专家

**存在理由**

生成专家容易延续自己的假设。审核专家使用独立规则对指定版本进行对抗性检查，并输出可定位的问题，而不是直接改写后宣称通过。

**主要判断**

- Schema、ID、版本和跨产物引用是否完整。
- 研究问题、方法、工具、变量和分析计划是否一致。
- 是否存在逻辑错误、测量污染、样本偏差、证据过度外推或遗漏反例。
- 是否涉及隐私、敏感金融信息、收益暗示、产品推荐或不当标签。
- 金融陈述是否能回到适用事实库和当前产品法律文件。
- IMA 接口状态、人工链接用途和来源措辞是否真实；AI 解释是否提前改变了原始认知测量。
- 是否误把知识题答错、“不确定”、年龄不愿回答或单一可疑信号直接当作无效答卷。
- 报告是否让首次阅读者明确知道研究对象、问题、指标和适用边界，专业术语与综合指标是否在第一次出现时解释。
- 问题严重度是 BLOCKER、MAJOR、MINOR 还是 WARNING。

**禁止事项**

- ReviewResult 不得冒充 ApprovalRecord。
- 不得由审核专家批准自己生成的研究产物。
- 不得只给笼统评价；每个问题必须有位置、证据和修改建议。
- 不得以“AI 判断风险低”替代合规、法务或有权限人员确认。

**建议收集的公开资料**

- 用户研究质量评价框架、效度、信度和偏差检查。
- 问卷质量审查清单、认知测试和逻辑验证规则。
- 定性研究的可信度、反例、研究者偏差和审计轨迹。
- 隐私、知情同意、数据最小化和去标识化规范。
- 监管机构或组织发布的金融宣传、投资者保护和适当性规范。

### CAP-05 证据与洞察专家

**存在理由**

该专家负责把答卷、逐字稿和执行记录转化为可复核的证据链，避免“先写结论，再找例子”。

在 Gate 1 前，它还可提供一次不落地为核心产物的预分析咨询：说明后续要比较什么、最低限度要收什么。ResearchBrief 仍由 CAP-01 负责，咨询不得提前产生用户洞察。

**V1 分析模块**

- 定性：资料熟悉、编码、主题、行为与态度区分、反例和原话定位。
- 定量：清洗口径、分子分母、题目 ID、筛选条件、缺失值和分组比较。
- 综合：Evidence Unit → Finding → Insight → Recommendation。
- 投教：从已经形成的 Insight 中识别投资者教育的内容重点、项目内适用人群、时点、候选形式、边界和验证方式。

**主要判断**

- 什么可以成为 Evidence Unit，如何定位到 Source Record。
- 哪些证据共同支持 Finding，哪些属于反例或矛盾证据。
- Finding 能否进一步解释为 Insight，以及有哪些替代解释。
- Recommendation 是否确实来自 Insight，并说明风险、假设和待验证项。
- 哪些 Recommendation 属于 `INVESTOR_EDUCATION`，以及学习需求、表达偏好和投教效果是否被正确区分。
- 候选分群和候选标签是否只在项目范围内成立。
- 单份答卷是否已从 `UNASSESSED` 解析为 `VALID`、`REVIEW_REQUIRED` 或 `EXCLUDED`，整体数据集是否为可分析状态。

**禁止事项**

- 不补写听不清的原话，不把摘要标为逐字引用。
- 不从一个参与者推导普遍规律。
- 不省略分子、分母、筛选条件或样本范围。
- 不把相关关系写成因果关系。
- 不把学习资源、AI 模拟用户或未纳入资料作为研究证据。
- 不自动创建正式客户标签或业务决策。

**建议收集的公开资料**

- 主题分析、框架分析、编码本和定性审计轨迹。
- 负例分析、三角验证、研究者一致性与反思性。
- 问卷清洗、描述统计、交叉分析、效应量和不确定性表达。
- Mixed-methods integration、joint display 和矛盾证据处理。
- 从 finding 到 insight、从 insight 到 recommendation 的案例标准。

### CAP-06 研究报告表达专家

**存在理由**

该专家把已通过 Gate 3 的 InsightPackage 转化为业务方可读报告，但不能在表达阶段创造新发现或改变证据强度。

**主要判断**

- 不同读者需要看到哪些层级的信息。
- 执行摘要是否忠实回答研究问题。
- 证据、发现、洞察、建议和限制如何清晰呈现。
- 如何在不改变上游证据的前提下，单独呈现“投资者教育建议”；证据不足时如何明确降级。
- 哪些细节进入正文，哪些进入方法或证据附录。
- 如何用一致口径表达不确定性、样本范围和未回答问题。
- 如何用“主张—证据—含义—边界”组织章节，并为每张图限定一个主要判断。
- 如何在每个重要数据段落开头提供上下文锚点，并把专业术语、综合指标和分群口径解释到首次阅读者能够独立理解。
- 如何选择不误导的图形、保存图表来源与变换，并提供图注、替代文本和逐页渲染复核。

**禁止事项**

- 不新增 InsightPackage 中不存在的数字、原话、发现或建议。
- 不为了叙事流畅隐藏反例和限制。
- 不把 Recommendation 改写成已批准 Business Decision。
- 不把候选研究标签写成正式客户事实。
- 不自行扩大报告分享范围。

**建议收集的公开资料**

- 用户研究报告、执行摘要和证据叙事的成熟模板。
- 定性与定量结果的可视化和不确定性表达。
- 面向产品、投研、运营或管理层的分层报告方法。
- 研究建议的优先级、风险、假设和验证计划表达。
- 金融研究报告的合规表达、引用和披露规范。

## 4. CTRL-01 研究总控概述

研究总控不是“最聪明的研究专家”，而是受规则约束的流程控制者。

**负责**

- 识别项目当前状态和可执行任务。
- 检查上游 Artifact、版本和 ApprovalRecord 是否满足前置条件。
- 把任务路由给对应专家能力。
- 触发自动校验、ReviewResult 和人工 Gate。
- 根据问题位置退回最早出错的产物。
- 保存交接记录，但不把聊天内容当作正式状态。

**不负责**

- 不替专家生成研究结论。
- 不越过 Gate 或伪造人工批准。
- 不在不同专家输出冲突时自行选择“喜欢的答案”。
- 不直接访问完成当前路由所不需要的个人数据。

**建议收集的公开资料**

- 状态机、任务编排、幂等、重试和版本冻结。
- Artifact-driven workflow、human-in-the-loop 和审批流。
- 多 Agent 的职责隔离、上下文最小化和失败恢复。
- 工作流可观测性、运行日志和回归测试。

## 5. 不建议做成专家 Agent 的组件

| 组件 | 推荐定位 | 原因 |
|---|---|---|
| 问卷平台 | Adapter | 智能发行、回收和导出是确定性接口能力，不决定分析口径 |
| Excel 答卷导入 | Adapter + Human Check | 负责字段映射、脱敏、规范化和质量状态执行，不负责生成洞察 |
| IMA 知识库 | Manual Learning Link + Dormant Adapter | V1 只启用人工学习链接；OpenAPI 搜索、正文读取和问答保留接口但不调用 |
| 转写与录音 | External Tool | 负责采集和转换，不负责研究解释 |
| FieldworkPackage 整理 | Service + Human Check | 按 InstrumentSpec 执行质量规则，登记资料清单、答卷状态、数据集状态、脱敏和版本 |
| Schema 校验 | Deterministic Validator | 应由代码稳定执行，不依赖模型判断 |
| 研究资产归档 | Storage/Index Service | 负责保存、权限和检索，不负责生成洞察 |
| 人工 Gate 审批人 | Human Role | 必须具有真实权限和责任，不由 Agent 模拟 |

## 6. 每张完整能力卡的统一结构

后续每张能力卡至少包含以下十二项：

1. `capability_id`、名称、版本和适用范围。
2. 触发条件与不应触发的场景。
3. 职责和唯一核心产物。
4. 必需输入、可选输入及允许访问的数据范围。
5. 核心判断规则和方法选择规则。
6. 标准输出及对应 Schema。
7. 允许动作。
8. 禁止事项和合规边界。
9. 自检清单和自动校验。
10. 失败条件、信息不足处理和升级对象。
11. 交接条件、目标 Gate 和退回路径。
12. 正向、边界、对抗和回归测试案例。

如果未来将能力卡封装为可运行 Skill，主体应保持简短；问卷、访谈、定性分析、定量分析和金融合规等详细方法放入按需加载的 `references/`，稳定且容易出错的校验放入 `scripts/`。

## 7. 资料采用结果

第一轮权威资料检索与方法 Skill 对照已经完成，详见[专家能力卡来源与采用记录](../references/expert-capability-source-register.md)。能力卡采用的核心原则包括：

- 研究问题面向“需要学习什么”，问卷和访谈题面向“如何向参与者提问”，两者分开。
- 组合研究必须有整合目的；不能因同时收集定性和定量就自动提高证据强度。
- 问卷题目需检查单一概念、中立性、题序、选项、路由、敏感性和预测试。
- 访谈优先获取具体行为、事件、过程、反例和替代做法。
- 定性与定量证据统一进入可定位证据链；统计显著不等于业务重要或因果。
- 报告只能压缩和呈现已批准洞察，不得提升主张强度。
- 金融合规、个人信息和正式 Gate 必须保留人类责任。
